# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

DarsAI is a Telegram bot that tutors students in math. Its home screen is a course picker: Math is live, and Physics, Chemistry, Biology, the AI course, Astronomy and Konkur are listed as coming soon (🔜). FastAPI receives Telegram webhook calls, python-telegram-bot handles the commands, an OpenAI-compatible LLM (Groq by default) does the tutoring, and an optional PostgreSQL database (Neon in production) stores memory, progress and usage. There is no web frontend. It needs Python 3.10 or newer.

Work happens on `develop`. PRs go to `main`, and Render deploys from `main`. There is no `render.yaml`, so the Render service settings exist only in the Render dashboard.

## Commands

```bash
pip install -r requirements.txt
python -m unittest discover -s tests -t .                                          # all tests
python -m unittest tests.test_math_shared.SolverTests                               # one class
python -m unittest tests.test_math_shared.SolverTests.test_linear_and_quadratic     # one test
python run_local.py                                                                 # local bot, long polling
uvicorn main:api --host 0.0.0.0 --port $PORT                                        # Render start command
```

- GitHub Actions (`.github/workflows/tests.yml`) runs two checks on every push and pull request, on Python 3.11: "Tests" (everything, in-memory storage) and "PostgreSQL tests" (`tests/test_postgres.py` against a PostgreSQL 18 service, the same major version as Neon in production; change both together).
- `tests/test_postgres.py` runs the SQL against a real database and is skipped unless `TEST_DATABASE_URL` is set. Each test drops every darsai_* table first, so the tests refuse a database whose name doesn't contain "test", and a server that isn't UTF-8 (psycopg would return text as bytes). Locally, with a throwaway server (see Local environment gotchas) and `createdb darsai_test`: `TEST_DATABASE_URL=postgresql://postgres@127.0.0.1:55432/darsai_test python -m unittest tests.test_postgres`. Add a test there for every new or changed SQL statement.
- Run tests as modules of the `tests` package. `tests/__init__.py` sets environment variables before `config.py` is imported: a fake bot token, an empty `DATABASE_URL` so the in-memory fallbacks are used, and `FREE_DAILY_AI_LIMIT=3`. The tests never call Telegram, an AI provider or a database.
- No linter or formatter is configured. Package versions are pinned in `requirements.txt` (Render installs from it).
- `run_local.py` is local dev mode. It uses long polling with a separate BotFather test bot and reads `.env.local`, which is git-ignored. It takes the bot token only from `LOCAL_TELEGRAM_BOT_TOKEN` and the database only from `LOCAL_DATABASE_URL` (empty means in-memory). It sets a placeholder `WEBHOOK_URL` before importing `main`, because `main.py` raises an error at import time without one, and then reuses `main.telegram_app`. Its `post_init` refuses to start if the bot already has a webhook, because polling deletes the webhook and would take production offline. Keep this guard. Render never runs this file, so `main.py` stays webhook-only.
- To check handlers without Telegram, send real `Update` objects through `main.telegram_app` and mock `reply_text`, the callback-query methods and `ai.call_ai_provider`.
- All settings come from environment variables, which `config.py` reads at import time. `.env.example` lists every one of them.

- **Webhook:** the webhook handler compares the `X-Telegram-Bot-Api-Secret-Token` header with `config.WEBHOOK_SECRET_TOKEN` and returns 403 if they don't match. The secret is `TELEGRAM_WEBHOOK_SECRET`, or a SHA-256 hash derived from the bot token if that is unset. The handler puts the update on `telegram_app.update_queue` and returns immediately, so a slow AI reply never holds the HTTP request open. `GET /` must not reveal the webhook path, and a test checks this.
- **Startup (`lifespan` in `main.py`):** brings the database schema up to date with `init_databases()` (`migrations.migrate()`; also used by `run_local.py`), starts the Application, sets the "/" menu (/start, /help and /privacy, in English and Persian) and the bot's description and short description (`setup_bot_descriptions`: `bot.description` / `bot.short_description` in English and Persian, set only when they differ, a failure only logged; `run_local.py` does both too), then calls `set_webhook` with the secret. Shutdown closes the database pool.
- **Button interface:** new buttons use callback data `d1:<owner user id>:<route>[:<arg>…]`, built with `Screen.button()` / `core.pack()` (Telegram's limit is 64 bytes). `router.callback_router` rejects presses by anyone but the owner with a pop-up, then dispatches on the first route part through `ROUTES`. Course screens are `c:<course>[:<screen>…]` (`ui/courses.course_route`): every Math button starts with `c:math` (`practice.MATH`), e.g. `c:math:prac:n:quadratics`. The top-level `learn`, `prac`, `tutor`, `solve` and `plot` routes from before courses stay in `ROUTES` as Math aliases, so buttons in older messages keep working. Other routes: `home`, `cont` (▶️ Continue), `su` (setup), `set`, `prog`, `prem`. An unknown route shows "coming soon". Screens draw with `Screen.show()`, which edits the pressed message and falls back to sending a new one (e.g. when the message is a photo). Every `Screen` handler call ends with the button press answered.
- **Old buttons:** buttons in old messages (`menu:math`, `main:*`, `math_level:*`, `math_action:*`) open the new screens through `router.OLD_BUTTONS`, drawn for whoever presses them (they have no owner); `menu:math` opens the Math hub and `main:subscribe` opens 💎 Premium. Only `ai:newchat` (`ai.py`) keeps its old handler. `router.register_fallback_handlers` must be registered last: it answers any button nothing else knows, so Telegram never shows an endless spinner. `/math` and `/mathhelp` show the new menu.
- **Groups:** commands and replies sent as the group (anonymous admins) or as a channel share one user id, so a handler in group -1 asks them to post as themselves and stops the update. When the bot is added to a group (`my_chat_member`) it explains `/start` and replying. In forum groups, messages sent after a button press go to that topic (`Screen.thread_id`).
- **Personal data:** give every new table with student data a `user_id` column (Delete my data finds tables by it), add a new in-memory store to `privacy._MEMORY_STORES` and a new per-process cache to `forget_in_process`, and update `docs/data-inventory.md` and the policy.
- **Languages:** the interface language is the student's choice (setup or Settings), or a guess from their Telegram language code. Keyboards are mirrored for Persian (`core.arrange`, and `menu_reply_keyboard` for the bottom keyboard). Private chats also get a persistent bottom keyboard, [🏠 Menu] [▶️ Continue]; each label works in either language (`MENU_LABELS`, `CONTINUE_LABELS`).
- **Courses (`modules/courses.py`):** `COURSES` is the one place a course is defined: id (used in routes and `darsai_course_notify`, never change one), emoji, name in each interface language (`names`, the one exception to "all text in i18n"), kind (`SUBJECT`, `PATH`, or `EXAM` for Konkur, which gets its own row under the grid), `live`, the hub's buttons (`hub`: `next` = ▶️ Practice: the suggested topic on its own row, the rest two per row from `ui/courses.HUB_BUTTONS`), and the AI tutor's role and rules (`tutor_prompt`; `math_tutor_prompt` is the Math one, unchanged from before courses). A course that isn't live shows "🔜" and its `soon.<id>` i18n text with 🔔 Notify me (`c:<id>:n`, saved once per student and course with their language in `darsai_course_notify`). The Math hub's 🎯 Konkur Math 🔜 (`c:math:konkur`) is the Konkur 🔜 screen with 🔙 Math. Tutor rules for courses that aren't live are drafts, not used yet. The order of `COURSES` is the grid's: school subjects first, then the path courses. A removed course (Astrology, replaced by Biology) keeps its `darsai_course_notify` rows; its old buttons show the expired pop-up, and `notify.notice_summary` (`/stats`) counts only the courses in `COURSES`.
- **Home and ▶️ Continue (`ui/home.py`, `ui/courses.py`):** home is ▶️ Continue, the course grid, 🎯 Konkur 🔜, then 📊 Progress, 💎 Premium, ⚙️ Settings. `continue_target` picks, in order: the unfinished practice question in this chat (under 24 hours: `practice.reopen_question` shows it again with the tries left), else a new question in the topic practised last (`get_mastery` is most recent first), else "▶️ Start:" with the weakest topic of the student's level (`practice.weakest_topic`, also the hub's ⭐ Suggested next and Progress's suggestion). The bottom keyboard's ▶️ Continue does the same. Each screen's first line says where the student is: "course · level › topic" (`practice.where`); Math screens have 🔙 Math (`practice.back_button`), and 🔙 Math leaves any open tool like 🏠 Menu does.
- **Setup and the bottom keyboard (`ui/setup.py`):** `/start` in a private chat asks students without `setup_done` three questions in one message (language, level, first course: `su:l:<lang>`, `su:v:<level>`, `su:c:<course>`). The last answer sends "✅ All set!" with the bottom keyboard and opens the course in a new message (a 🔜 course opens its 🔜 screen). Migration 1 adds `setup_done` and `keyboard_version` to `darsai_student` when they are missing, and then marks every student any table knows as set up, so only new students get the questions. `keyboard_notice` (a `TypeHandler` in group -1, after the anonymous-sender check, before the screens) sends set-up students whose `keyboard_version` is below `setup.KEYBOARD_VERSION` the current bottom keyboard once with `keyboard.notice`, private chats only; `claim_keyboard_version` is one UPDATE, so two updates at once can't both send it. `/start`'s welcome and finishing setup bring the keyboard, so they count. A per-process set (`setup._current`) keeps it to one check per student. To change the bottom keyboard later, raise `KEYBOARD_VERSION` and write a new notice.
- **Migrations (`migrations.py`):** `migrate()` creates `darsai_schema_version` (one row per applied migration) and applies the missing migrations in order. Each runs in its own transaction holding `pg_advisory_xact_lock(LOCK_KEY)` and checks again, once it has the lock, that it isn't applied yet: two instances starting together (old and new during a deploy) apply it once, a failure rolls the whole migration back and stops startup, and transaction-level locks also work through Neon's pooler. Once it has the advisory lock, a migration waits at most `MIGRATION_LOCK_TIMEOUT_SECONDS` (default 5, `set_config('lock_timeout', …, true)`) for table locks, so an `ALTER TABLE` stuck behind a long query fails fast (the deploy fails, the old instance keeps serving, the next start retries) instead of making every query on that table wait behind it. Migration 1 is the schema as of 2026-11-22: every `CREATE TABLE` / `ADD COLUMN` the old `init_*_db` functions ran (word for word), with their "only the first time" backfills, so a database of any older version comes out fully up to date and production only records version 1. A database newer than the code (after a rollback) is only a warning. Without a database, `migrate()` does nothing.
- **Storage:** every storage function has two branches. When `db_configured()` is true it uses PostgreSQL. Otherwise it uses a module-level dict: `_MEMORY_FALLBACK` and `_USAGE_FALLBACK` in `ai.py`, `_FALLBACK` in `student.py`, `input_mode.py`, `activity.py` (plus `_FIRST_SEEN`), `premium.py` and `notify.py`, and `MASTERY_FALLBACK` and `ACTIVE_QUESTION_FALLBACK` in `shared.py`. Tests run against these dicts and clear them in `setUp` (plus `stats._seen` and `setup._current`); `TelegramMocks.existing_student()` marks the test student as set up. The tables are `darsai_ai_messages`, `darsai_ai_usage`, `darsai_student`, `darsai_user_profile`, `darsai_mastery`, `darsai_active_question`, `darsai_input_mode`, `darsai_daily_activity`, `darsai_premium_waitlist`, `darsai_course_notify` and `darsai_first_seen`. Settings (language, level, `setup_done`, `keyboard_version`) are per student in `darsai_student` and follow them into every chat; `darsai_user_profile` is only read as a fallback for levels saved per chat before that. Mastery is per student too (`user_id, level, topic`). The old per-chat `darsai_math_progress` table (still in production) is never written; migration 1 copied its counts into `darsai_mastery`, once ever, for topics a student had no mastery row for, so deleted progress can't come back from it. The active practice question is keyed by `(chat_id, user_id)`, so students in the same group chat don't share it.
- **AI calls:** `ask_ai_with_memory()` takes one message from the daily limit (`reserve_ai_message`, an atomic SQL upsert that also counts messages when there is no limit, because `/stats` reports them), loads the history for `(chat_id, user_id, topic)`, calls the provider, gives the message back if the call fails, and saves the exchange. Memory topics are `general` for `/chat`, `math` for the tutor answer from `/solve`, and the canonical topic name (such as `quadratics`) for `/math_tutor`. `provider_config()` picks the URL and API key for groq, openrouter or openai. All three use the OpenAI chat-completions format through `httpx`. The default `AI_MODEL` is `qwen/qwen3.8-27b` (Groq): Groq removed `llama-3.1-8b-instant`, and of the models tried it gave the best casual Persian and plain text (`gpt-oss-20b` answered in Arabic, `gpt-oss-120b` spent most of `max_tokens` on hidden reasoning). `call_ai_provider` removes `<think>…</think>` reasoning (`strip_reasoning`) before an answer is sent or saved, and treats an answer that is empty afterwards as a failure, so the daily message is given back. A `model_not_found` / `model_decommissioned` error raises `AIModelUnavailable`, whose logged message names `AI_MODEL`; fixing it means changing `AI_MODEL` (on Render: the service's Environment settings).
- **Math flow:** `TOPIC_MODULES` in `topics.py` maps `(level, topic)` to a module that has `lesson()` and `practice(difficulty)`, and `DEFAULT_TOPIC` gives each level's fallback topic. Topic names are unique across levels (`TOPIC_LEVEL`), because callback data and AI memory use the topic alone. `/solve` uses `solve_equation()`, which fits a polynomial through x = 0, 1, 2, checks the fit at five more points, and raises `UnsupportedEquation` for anything that isn't linear or quadratic.
- **Practice flow (`ui/practice.py`):** the ✍️ Practice button and `/practice` both call `new_question()`, which saves the question (with an `id`, `attempts`, `mode` and the `message_ids` that show it) as the active question. Answers come from typed text in private chats (`home.text_message`), replies to those `message_ids` in groups (`group_reply`) and `/check`; all go to `handle_answer()`. Text that `readable_answer()` can't read doesn't use a try. A wrong answer gets one more try, then the solution. `finish()` removes the question with `clear_active_question(..., question_id)` first, so a result counts once, then calls `record_answer()`. Difficulty mode `a` uses `recommended_difficulty(mastery)`; `e`/`m`/`h` (🔽 Easier / 🔼 Harder) pin it. Typed text stops counting as an answer after 24 hours.
- **Typed text (`ui/typed.py`):** in private chats the 🏠 Menu label opens home and clears the input mode, and the ▶️ Continue label does ▶️ Continue. Otherwise text goes to the open tool (tutor, solve, plot; `tools.current_mode`), else to the active practice question, else the student gets a nudge to the menu. Pressing a tool sets the input mode (`tools.start_mode`); the Menu button, `/start` and a new practice question clear it, and it ends after 24 hours. Opening a tool keeps the practice question, so after Menu typed text answers it again. In groups only replies count: to the tool's `message_ids` first, then to the practice question's. Change a stored input mode only with `change_input_mode` (one locked step, only while it has the same `id`, and only the fields given), never by writing back a state read before a slow tutor call.
- **Tools (`ui/tools.py`):** the tutor's memory topic is `math`, or the lesson's topic when opened from 📘 Learn. Their answers have 🔙 Math. Solve shows `solve_equation()` results in the student's language: `SolveError.code` picks the message (`str(error)` stays English for the old `/solve`), and results get a 🧑‍🏫 Explain step by step button that asks the tutor once: `claim_last_result` lets only one of two quick taps through. Plot uses `parse_plot_input` and `create_plot` from `plot.py` and sends a photo. Solve and Plot show their `EXAMPLES` as copyable code and as one-tap buttons (`c:math:solve:e:<i>`, `c:math:plot:e:<i>`, which reopen the tool if needed), and answer input with several lines with "one per message".
- **Premium (`ui/premium.py`):** Premium isn't built. The screen says so, lists what it will add, and asks what the student wants most: one button per `premium.CHOICES` entry, several allowed. Each press is saved at once (`premium.set_choice`), with where it was pressed (`menu` or `limit`) and the student's language for the later announcement. Buttons carry their action (`prem:a:<choice>:<m|l>` adds, `prem:r:…` removes), so a stale button does what its label says. A student is on the waitlist while they have a pick. The tutor's daily-limit message (`limit_view`) shows the same picks only to students with none yet; the old commands' English limit text points to `/subscribe`.
- **Stats (`stats.py`):** `track_activity` (a `TypeHandler` in group -2) notes each student once per UTC day in `darsai_daily_activity`: button presses, private messages, and in groups commands and replies. Not posts as a group or channel, bots, or `my_chat_member`. A per-process set (`_seen`) keeps it to one write per student per day, and a failure is only logged. `record_answer` adds `practice_answers` in its own transaction. The first time the tracker sees a student it also writes `darsai_first_seen`, with the start-link source when the update is `/start <source>` in a private chat (`t.me/<bot>?start=<source>`, `activity.valid_source`: letters, digits, `_`, `-`, at most 64). That row is never changed, so only new students get a source. When migration 1 creates `darsai_first_seen`, it copies in every student the other tables know, with their earliest timestamp, so existing students don't count as new. /stats also counts 🔔 Notify me per coming-soon course (`notify.notice_summary`). Admins (`ADMIN_USER_IDS`) are left out of every `/stats` number (`user_id <> ALL(%(admins)s::bigint[])`). `/stats` answers only user ids in `ADMIN_USER_IDS`, only in private chats, in English (`admin.admin_command`, which every admin command uses). `config.parse_admin_ids` never fails: it strips quotes, and anything that still isn't a number is skipped and logged as a warning at startup (`stats.log_admin_setting`), so a typo can't stop the bot. Anyone else gets no reply, and the sender's user id is logged at INFO (that's how an admin finds their id). Active students also count tutor use (`darsai_ai_usage`) and practice (`darsai_mastery.updated_at`) from before the daily table existed.
- **Error alerts (`alerts.py`):** a logging handler on the root logger (and `uvicorn`, which doesn't pass records up) sends every ERROR record to each admin in `ADMIN_USER_IDS` from the bot itself, so staging and the local test bot alert from their own bot. It starts with the bot (`start_alerts` in `lifespan` and `run_local.py`'s `post_init`; `stop_alerts` waits for alerts still being sent). An alert has the error type and message, the last place in our own code (`file:line in function`), the log message and the time, cut to 300 characters, never the update, local variables or request data, and `scrub()` replaces every secret (the bot token and anything shaped like one, the webhook secret, a custom webhook path, the AI keys, the database URL and URL passwords, the Sentry DSN). The same kind (logger, message template, exception type, place) goes out at most once per `ALERT_REPEAT_MINUTES` and the next one says how many were held back; at most 10 alerts per window in all. A failure to send is logged at WARNING by `modules.alerts`; records from that module and anything logged while an alert is being sent are never alerted, so it can't loop. `ALERTS_TO_ADMINS=false` turns them off. Sentry (`init_sentry`, at import of `main.py`) only when `SENTRY_DSN` is set: the SDK is imported only then, with `data_collection` off for user info, headers, bodies, query strings, AI inputs and frame variables, no auto-enabled integrations (they would record Telegram URLs and webhook bodies), and `before_send` / `before_breadcrumb` dropping request data and HTTP breadcrumbs and scrubbing the rest. The console (stdout and stderr, which is Render's log) is scrubbed the same way: `scrub_console_logs()` (in `main.py`, right after `basicConfig` and before `init_sentry`) wraps the formatter of every handler on the root and uvicorn loggers in `ScrubbingFormatter`, tracebacks included, and replaces `sys.excepthook` and `threading.excepthook`; uvicorn's access lines thus hide a custom webhook path too. Sentry keeps WARNING and above as breadcrumbs, not INFO (those lines hold user ids). `/alerttest` (admins) raises a test error containing `FAKE_TOKEN`, a value shaped like a bot token, never the real one, so both the alert and the log must show `[redacted]`.
- **Privacy (`privacy.py`, `ui/privacy.py`):** ⚙️ Settings → 🔒 Privacy and `/privacy` show the policy (`privacy.*` strings); it names who receives data from the settings in use: the AI provider (`AI_PROVIDER` via `AI_PROVIDER_NAMES`), Sentry only when `SENTRY_DSN` is set, and `PRIVACY_CONTACT` only when set (empty in the code; set on Render). `/privacy` is in Telegram's "/" menu with /start and /help, because Telegram's "Privacy Policy" in the bot's profile opens it only then. 🗑 Delete my data (`priv:d`, also `/deletemydata`) asks first; `priv:d:y` runs `privacy.delete_student`: in one transaction it deletes the student's rows from every darsai_* table with a `user_id` column (except today's `darsai_ai_usage` row, so deleting can't reset the daily tutor limit; `drop_kept_usage`, at startup and after each delete, removes past days' usage rows of students with no `darsai_first_seen` row, i.e. kept rows once their day is over), found from `information_schema` when it runs (so new tables and the old `darsai_math_progress` are covered), in every chat; without a database it clears every store in `privacy._MEMORY_STORES` (a test checks every module-level fallback dict is listed). Then `ui/privacy.forget_in_process` clears the per-process caches with user ids (`stats._seen`, `setup._current`, PTB's `user_data`): add any new one there. The student is new afterwards (setup again, counted as new). It logs only counts. `docs/data-inventory.md` lists everything stored and why; update it and the policy together when data or a receiver changes. Still to do: the backup AI provider (Phase 1 step 8) must be named in `privacy.receivers`, and when tutor-memory pruning lands (step 11: newest 16 messages per conversation, nothing older than 90 days) the retention goes into `privacy.stored` in both languages and into `docs/data-inventory.md`; step 11's daily cleanup should call `privacy.drop_kept_usage` too.
- **Settings:** `config._int_env` / `_bool_env` never fail on a typo: they keep the default and add a line to `config.SETTING_WARNINGS`, which `start_alerts` logs at startup. Use them for new number and true/false settings.
- **Imports:** `modules/math/__init__.py` deliberately doesn't import `math.py`, so `shared.py` and the topic modules can be imported without python-telegram-bot.

## Conventions to keep

- Database functions are synchronous. Handlers must call them with `await asyncio.to_thread(fn, ...)`, never directly. Use `with connection() as conn, conn.cursor() as cur:`. The pool commits on success and rolls back on error.
- The schema lives only in `modules/migrations.py`. To change it (a table, a column, an index, a backfill), add a migration at the end of `MIGRATIONS` with the next version number, and a test in `tests/test_postgres.py`. Never edit a migration that is on `main`: databases that have it never run it again. Migrations run once at startup (`main.init_databases()` in `main.lifespan`), never per request.
- Every AI call goes through `ask_ai_with_memory()`, which charges the daily limit and refunds it if the call fails. Show users `ai_error_message(error)` (old commands) or `tools.ai_error_text(screen, error)` (buttons, translated), never the raw error. Both log through `log_ai_error`.
- Send AI output with `reply_long()` (old commands) or `Screen.send_long()` (buttons) so replies over 4000 characters are split. It is sent as plain text, so every tutor prompt includes `common.PLAIN_TEXT_RULE` (no Markdown, no LaTeX, Unicode math).
- Math input goes through `Expression` / `safe_eval` (an AST whitelist). Never use `eval`.
- Topic memory keys are canonical topic names (`linear_equations`, `quadratics`, …). Add aliases to `TOPIC_ALIASES` and new topic modules to `TOPIC_MODULES` in `topics.py`, plus a `topic.<name>` string in both languages. `MATH_MEMORY_TOPICS` is derived from `TOPIC_MODULES`.
- Practice generators take `"easy"`, `"medium"` or `"hard"` and return `{level, topic, difficulty, prompt, formula, answer, steps}`. `prompt` is a `prompt.<key>` string, `formula` a list of formula lines, and each step is `[key, params, formula]` for a `step.<key>` string. Step params are positive integers (a minus sign inside a Persian sentence gets reordered; use `number_step()`), and the last step's formula shows the answer. Format polynomials with `poly_text()`. `answers_match()` compares answers by value. The whole dict must survive a JSON round trip.
- `lesson()` returns `{level, topic, intro, example}`: `intro` is a list of `[full i18n key, params, formula or ""]`, and `example` is `{prompt, formula, steps}` in the practice format.
- Text students see in the button interface comes from `modules/i18n/en.py` and `fa.py`, never inline strings. The one exception is course names, in `modules/courses.py`, so a course is defined in one place (a test checks every course has every language and every 🔜 course a `soon.<id>` text). Level names (`level.*`) are the grade names: "Grades 7–9" / «متوسطه اول (هفتم تا نهم)», "Grades 10–11" / «دهم و یازدهم», "Grade 12 · Konkur" / «دوازدهم و کنکور», "University" / «دانشگاه». Add every key to both files with the same `{placeholders}` (a test checks this). Persian uses casual «تو», and the user reviews all Persian text. Put formulas on their own line instead of inside a Persian sentence (`practice.formulas()` adds the left-to-right mark). Examples students may send back use `formulas(..., copy=True)`: they go out as Telegram code entities, so one tap copies just that line.
- Messages are plain text: never use `parse_mode`. Formatting is done with entities: `core.copyable()` marks text and `Screen.send`/`show`/`send_photo` turn the marks into code entities (offsets in UTF-16 units). Send through `Screen`, or the marks show up as odd characters.
- Everything students type goes through `strip_invisible()` (inside `normalize_expression`, `parse_plot_input` and `tools.handle_input`): a formula copied from a Persian message carries a left-to-right mark. A `/command` inside a Persian sentence needs `\u200e` right before it, or it shows as "start/" (a test checks this).
- Keep the httpx logger at WARNING (set in `main.py`). Its INFO logs include request URLs, and Telegram URLs contain the bot token.

## Local environment gotchas

- The default `python` is Anaconda base 3.8 with no dependencies, so tests fail with `No module named 'fastapi'`. python-telegram-bot 22.7 needs Python 3.10+. Suggested setup: `conda create -n darsai python=3.11 -y && conda activate darsai && pip install -r requirements.txt`.
- A 3.11 interpreter exists at `/Users/ali/opt/anaconda3/envs/rota/bin/python`. That env belongs to another project, so use it only to create a separate venv and never install into it.
- PostgreSQL binaries for a throwaway test database are in `/Users/ali/opt/anaconda3/envs/rota-pgtools/bin/` (`initdb`, `pg_ctl`, `createdb`). Run `initdb -E UTF8 --locale=C --auth=trust -U postgres`: without `-E UTF8` it can create an SQL_ASCII cluster on this Mac, and then psycopg returns bytes and every Postgres test fails with odd errors. Listen on 127.0.0.1 with a custom port, and delete the data directory afterwards.
- The `gh` CLI is not installed, so PRs can't be opened from the terminal until the user runs `brew install gh` and `gh auth login`. Until then, push and let the user open the PR on github.com. `git push` uses the macOS Keychain login. Always ask the user before pushing.

## Deploying

After a merge to `main`, Render redeploys. On startup the bot applies any new migrations (the log says "Database schema version N."; a failed migration stops startup and changes nothing) and registers the webhook again with the secret. To check it, open `https://api.telegram.org/bot<TOKEN>/getWebhookInfo`: `last_error_message` should be empty. Don't paste the token anywhere public. In production, set `DATABASE_URL`, because the in-memory fallbacks belong to a single process and are lost on restart.
